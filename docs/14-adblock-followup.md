## 各阶段具体发生了什么

| 阶段 | 问题与改动 | 检查与后续反馈 |
|---|---|---|
| r3 | 对知乎 API 的 UDP/443 做定向实验 | 冷启动无开屏曾获反馈；切回前台仍弹广告，不能据此认定传输是唯一原因 |

| r7 | 结合复核意见补入口匹配，加入限时、去参数的阶段诊断 | 人工 JSON/gRPC 检查通过只能证明检查页链路，不能证明真实应用流量经过 |
| r8 | 将两个知乎接口从空体 Map Local 改为明确返回 `{}`；B 站增加请求阶段观察 | Mac 验证为 200、2 字节；用户随后确认 B 站对应广告位消失，知乎切回广告仍在 |
| r9 | 精准空 JSON 处理补充 `real_time_second_floor_v2` | 接口处理检查通过；用户后续仍报告知乎切回广告 |
| r10 → r11 | 从手机连接记录发现广告 SDK 入口及备用地址，逐步补充精确拒绝规则 | 实际日志区分了已被拒绝和仍放行的入口；命中证据仍不等于最终广告效果 |
| r12 | 将已识别广告 SDK 扩展为 11 条域名组规则；与所取来源中的 68 个相关域名对照 | Mac 30 个拒绝探针包含 6 个合成变体，正常域名控制项通过；用户随后报告 B 站异常且知乎广告仍在 |
| r13 | B 站改用小型同步过滤，停用十项可选或有兼容风险的挂接，移除一项播放地址响应处理；知乎补两个精确广告 API | 模拟过滤、规则回放和 Mac 接口检查通过；手机恢复及广告效果待确认 |

r12 日志中没有观察到 B 站域名被新增域名组拒绝，不能据此排除 HTTPS 处理、脚本挂接或其他兼容问题。原首页脚本的联网补位与广泛请求观察器是 r13 减少的潜在负担；尚未隔离出手机异常的唯一原因。

## r13 的兼容性取舍

本地新写的 [bili_feed_safe.js](../src/bili_feed_safe.js) 只对选定首页、短视频和开屏 JSON 做同步处理：删除明确标记的广告项或指定广告字段。没有广告、数据未知、错误、过大或非文本时原样放行；不补位联网、不改正常分页、视频地址或 URL。

它替代的是选定 JSON 路径的处理，不是 Biliverse 完整模块的重新实现。保留的 View / Reply 等处理仍来自上游；本仓库没有重新分发那些 bundle。源码及测试说明见 [参考源码](../src/README.md)。

知乎 r13 补充的两个精确入口是 `open.kuaishouzt.com`、`df.tanx.com`。在项目记录中，它们既有放行观察，也有 anti-AD 分类依据；Mac 后续命中拒绝。连接日志没有响应体和完整应用归属，不能断言它们就是这次广告的唯一来源。来源见 [更新来源记录](../data/update-source-attributions.json)。

## 诊断中值得保留的做法

1. **分开记录请求与响应。** 请求到达不表示脚本已解码、过滤并提交结果。零记录也不能直接解释为没有业务流量或一定是 QUIC。
2. **先核对客户端运行环境。** 脚本语法通过不代表目标引擎具备所需接口；人工数据回放也不代替真实手机。
3. **给诊断设期限与字段边界。** 原项目诊断采用短时窗口、固定分类和有限槽位，不记录账号、认证头、查询参数或正文。原始手机数据库另作本地私密分析，不放进公开问题单。
4. **把正常功能列为完成条件。** 去掉广告后仍需检查首页刷新、普通与竖屏视频、直播、连续播放、搜索与评论。出现异常时先减少挂接，保留可回退版本。
5. **保留失败结果。** r8 的局部成功、r12 的回归和 r13 的待验收同时成立。不要只展示最后一次返回 200 的检查。

## 读者怎样复测和回退

使用自己合法取得并审阅的模块，记录版本后更新，重连客户端，再分别观察冷启动与切回前台。先验收正常业务，再检查具体广告位；缓存条件、网络和应用版本分别记录。

遇到首页或播放异常，先停用新增模块或恢复自己已验证可用的版本，不同时替换节点、证书和分流。r12 已有异常反馈，不能把它当作已验收正常的推荐回退版本。未知设备需重新测试，不能直接采用本项目的私人交付结论。
