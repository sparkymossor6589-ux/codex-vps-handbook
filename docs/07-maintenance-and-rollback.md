# 维护与回退

维护的重点是让一次变化可以定位、验证和撤销。已可用的节点与配置作为基线，每次记录具体改动。

## 日常检查

| 检查对象 | 关注内容 |
|---|---|
| 服务器 | 服务状态、磁盘和内存、异常重启 |
| HTTPS | 有效证书、续期任务与加载结果 |
| 节点订阅 | 原参数是否保留，节点数量是否符合预期 |
| 分流 | 当前配置、策略组和几个常用域名的命中 |
| 在线更新 | 远端版本、回读内容和客户端当前版本 |
| 费用 | 实际账单、预算通知与流量使用 |
| 应用模块 | 上游变化、资源完整性、主要功能与误拦截 |

长期稳定性需要在持续使用中积累记录，单次检查不预填“长期稳定”。

## 一次更新的记录模板

```text
日期与环境：
本次目标：
执行前状态与备份：
具体改动：
来源、版本与哈希：
配置或程序检查：
服务器发布与回读：
客户端实际使用状态：
设备业务测试：
尚未验证：
回退方式：
```

## 回退顺序

1. 判断问题来自节点、分流、在线入口还是应用模块。
2. 优先停用对应新增模块或切回上一版文件。
3. 客户端刷新并确认实际使用版本，复测目标问题和基础联网。
4. 需要恢复服务端文件时，先保存当前状态，再使用对应备份。
5. 客户端数据库恢复须按客户端状态处理，运行期间不要直接覆盖。

流量累计状态、节点凭据与证书通常不属于一次规则回退的目标；确实需要修改时单独记录其影响。

## 接入权限与撤销

关闭网页入口只影响后续获取资源。已下载的节点是否仍能连接取决于服务端凭据；撤销某个用户时需要同时考虑入口与连接授权。

统一接入方式也意味着共享材料的影响范围较大。需要独立撤销能力时，应在自己的部署中设计独立凭据和更新路径，不能把历史的多个入口名称当作独立隔离的证明。

## 本地文件整理

先盘点，再把过时过程文件移入可恢复位置，并保留清单。保留当前交付、维护源码、来源索引、回退备份、原始验证记录及尚未完成的接入材料。

项目曾把重复交付和过程文件移到本机废纸篓。这说明清理可恢复，不代表服务器、客户端或其他设备同步完成了更新。

## 向他人分享前

从独立的公开目录打包。检查配置、截图、二维码、浏览器或命令输出、压缩包与历史文件中是否包含私人材料。发布前运行本仓库的基础检查工具，并对照 [SECURITY.md](../SECURITY.md)进行人工核对。
