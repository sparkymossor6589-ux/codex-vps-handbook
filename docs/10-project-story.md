# 从搭建到维护：这个项目的完整经过

这份记录根据本地材料整理，保留能够找到依据的阶段、问题和结果。日期反映文件记录的阶段，未据此补写逐条聊天时间。提示词是重新整理的示例，入口见[提示词合集](08-prompts.md)。

## 2026-10-11：先弄清自己需要怎样的服务器

前期材料围绕 VPS 提供商、费用、地区及实际使用证据做比较，也整理了三端接入准备与网络搭建案例。

当时的准备方案是 Mac / Windows 使用 Clash Verge Rev、iPhone 使用 Shadowrocket，并特别关注服务端与客户端的版本互通。后续实际落地的 Mac 使用了 Shadowrocket，安卓接入则在后面加入；Windows 没有完成交付与验收。准备方案与最终部署需要分开记录。

这一步让后续目标变得具体：需要自己的服务器、国内应用保持可用、Mac 和手机便于接入，并且后续更新不能反复从头操作。历史套餐数据和第三方使用报告只能作为当时参考，购买时仍需核对实际报价和自身网络。

**这一阶段可复用的做法**：把地区、预算、设备和业务交代给 Codex，要求它说明信息来源与日期，再进行具体账户和部署操作。

## 2026-10-20 至 21 日：完成服务器与 Mac 的基础连接

项目最终使用 AWS Lightsail 东京实例，部署 Xray 的 VLESS + REALITY + Vision。部署程序固定版本并校验压缩包，在服务器生成连接参数，检查配置后启动服务。

随后在 Mac 客户端检查节点、路由模式和实际联网。某次自动化页面出现加载失败，独立浏览器检查又通过，于是保留了差异，没有把页面异常直接当作节点故障。

**这一阶段可复用的做法**：让 Codex 执行环境检查、部署与技术核验，同时把真实业务是否成功单独确认。

## 2026-10-21：补充分流，再整理节点与流量显示

项目为国内应用、局域网和指定服务建立规则顺序，核对客户端实际命中；后续合并节点与估算流量订阅，减少列表中的重复项目。

流量来自服务器网卡计数，曾核对重启和跨月累计逻辑。记录一直保留“估算，不是 AWS 实时账单”的区别。

**这一阶段可复用的做法**：先固定已可用节点，再围绕明确应用修改规则；外观整理也要核对原参数与分流是否保持。

## 2026-10-21：从传文件发展到私人在线入口

手机最初有手动导入包，后来改为一个私人网页引导两次原生导入：节点订阅与在线分流。在线入口保持稳定，后续更新在对应对象中刷新。

用户随后确认 iPhone 在 Wi-Fi 和蜂窝下 ChatGPT 文字正常，截图也核对了指定海外业务和国内资源的分流。安卓接入采用 Mihomo 配置，经历独立交付到统一入口的整理，并处理了入口路径和分享参数导致的兼容问题。

安卓真机、iPad 等仍保留待测；服务器能发出配置不代替手机实际导入。

**这一阶段可复用的做法**：让 Codex 把导入对象、顺序和更新方法做成明确入口，再逐台设备确认使用结果。

## 2026-10-21 晚：从日常问题反推规则修补

用户反馈手机音乐蜂窝加载慢，另有一次出行应用还车失败。项目在 v3 中增加 9 条直连规则，检查 Mac 命中与远端回读。手机更新后的音乐效果没有完成确认，还车失败原因也未确定。

随后为 Steam 加入 v4：商店、社区和图片走节点，下载与专用更新地址直连。37 条新增规则完成解析和抽样检查，保留了共享 CDN 备用路径不能仅按域名完全拆分的边界。没有真实游戏长下载测速记录。

**这一阶段可复用的做法**：把“我的某个功能有问题”变成一个小范围任务，让 Codex 找依据、改规则、记录效果与不确定性。

## 2026-10-22：研究并整合常用应用去广告

项目先整理候选来源和阅读程度，再为首批 14 款应用整合独立模块与总模块。规则、脚本依赖、MITM 主机和重叠条件需要分别检查，不能只看项目标题就宣布可用。

r2 形成模块与依赖的版本化交付，进行服务回归、脚本语法与资源回读核对。这个阶段 Mac 曾完成模块导入，但模块停用、HTTPS 解密关闭、尚未设置信任。该状态是阶段记录，后续才发生变化。

**这一阶段可复用的做法**：把新增功能与已有主分流分离，读清上游内容，准备停用与回退路径。

## 2026-10-22：知乎仍有开屏，继续验证实际链路

手机反馈在模块和 HTTPS 解密开启、证书已信任之后，知乎开屏仍存在。项目没有停在“设置已经打开”的结论，继续针对实际传输路径设计实验。

r3 只增加针对知乎 API 的 UDP/443 定向拒绝规则，保留其余配置与版本化依赖，更新后用户确认手机知乎冷启动无开屏；后续补充熄屏 / 亮屏回前台仍弹广告，问题尚未完全解决。由于条件与观察范围有限，记录把它写成个人设备效果，不声称证明了唯一根因。

之后 Mac 单独生成 CA、设置信任并启用模块，对选定知乎接口做停用 / 启用对照，确认本机处理链路和基础联网。14 款应用在 Mac 的逐项效果仍未完成。

**这一阶段可复用的做法**：区分开关状态、请求实际处理和用户看到的结果；保持每次实验的影响范围清楚。

## 2026-10-22 后续：B 站适配、知乎补漏与正常功能回归

r5 / r6 经历了“离线样本通过、手机仍有广告”：Mac 原生执行查出引擎缺少 TextDecoder，切换入口运行引擎后样本通过，手机仍未确认成功。r7 因此补充限时诊断，r8 将请求阶段与响应阶段分开，另修正知乎两个接口的空体回包。用户随后确认 B 站对应广告位消失，知乎切回广告仍存在。

r9 精准补接口，r10 / r11 根据手机连接记录查广告 SDK 与备用入口；r12 把部分已知 SDK 扩展为域名组。Mac 的规则检查通过之后，手机却反馈 B 站首页刷新与播放异常，知乎切回广告仍在。这是一次必须记入项目经过的正常功能回归失败。

最新 r13 减少 B 站挂接、停用十项可选或有兼容风险的处理，并用不联网补位的小型同步过滤处理选定 JSON 路径；知乎另外补充两个有观察及分类依据的广告 API。模拟、Mac 接口和小段媒体请求检查通过，手机恢复和广告效果待验收。完整经过与各阶段边界见 [r3 → r13](14-adblock-followup.md)。

安卓另行整理 [GKD 自动点击跳过路线](15-android-gkd.md)，没有把小火箭模块包装成安卓已经上线的去广告更新，也没有补写真机成功。

**这一阶段可复用的做法**：把“不破坏首页和播放”写进完成条件；同时保留局部成功、后续回归与新版本待验收，减少缺乏设备证据时不断叠加规则。
